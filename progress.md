# Driver Progress (`S5L8947X` / `j33iap`)

Status of every hardware block, checked against the drivers in the tree and the enabled nodes in `s5l8947x-j33iap.dts`. Last reviewed 2026-11-02 on hardware (`hwtest`: 124 passed, 0 failed, 2 skipped, including `hwtest gpu` 10/10). The SGX driver was booted from the final bundle: microkernel handshake, a 2D transfer, the render node's GEM path, the `BLIT` ioctl, a contiguous buffer presented on HDMI through PRIME with the 2D engine drawing it, and a full-screen clear through the TA/3D queue (`sgxframe`, 1280x720 and 640x360, every checked pixel right) all work. See [SGX.md](SGX.md). For full cache, crypto, and ARM NEON benchmark tables, see [benchmarks.md](benchmarks.md).

### Wi-Fi known limits

- The first probe fails; `brcmfmac` attaches only after `stage2` has provisioned the firmware and re-probes the HSIC device (firmware up about 9 s after boot).
- The board's CLM blob is rejected by this firmware (`clmload` -52, which aborts the attach), so it is not provisioned and the firmware's built-in regulatory data is used (NVRAM default `ccode=XZ`, regrev 20); it still covers 2.4 and 5 GHz and accepts ISO 3166 countries. The factory system configuration has a region entry (`Regn`), which is not used: it names a sales region rather than where the device is used.
- HSIC runtime suspend stays off (USB default); enabling it needs the port's resume workaround.
- `stage2` selects the board's firmware files by name (one variable for both radios); another board in the family needs its own name there.

### Bluetooth known limits

- Not the stock 3 Mbaud: the UART's two clock sources measure about 51.3 MHz and 24 MHz, there is no fractional divider (the slot register does not latch), and 3,206,250 baud (51.3 MHz / 16) is not matched by the controller.
- This controller firmware sets extra high bits in the LE advertising report type, so the kernel logs "unknown advertising packet type" for some reports and drops them.
- Pairing and connections are untested (needs a device to pair with). Keyboards are supported in the kernel (`hidp` for Classic, `uhid` for LE through BlueZ), and pairings are kept on `Data` (`/linux/var/lib/bluetooth`, bind-mounted on `/var/lib/bluetooth`).

### RTC known limits

- The clock is set from the network: the DHCP lease hook starts busybox `ntpd` (`pool.ntp.org`) on the first lease (Ethernet or Wi-Fi), and its event hook writes the time to the PMU RTC once it is known. Without a network after a power loss, the clock falls back to the image build date until a lease arrives.
- The alarm fires and is reported, but waking the board from MCU standby with it is untested.

### Thermal known limits

- The trip points (70 C passive, 95 C critical on the SoC-side board thermistor) are estimates: the stock software sets none for this board. The thermistor sits on the board next to the SoC, not in the die, and lags the die temperature.
- The board has no SoC die sensor (its device tree has none), and the PMU's battery and calibration inputs (`tbat`, `tcal`) are fixed resistors on this board, so they are not exposed.

### Display known limits

- Pixel clocks are capped at 108 MHz, so 1080p runs at 30 Hz and below. At 121.75 MHz the sink sees bit errors (colours, tearing, dropouts) and from 146.25 MHz it does not lock, although the PHY reports lock with the stock configuration and the PHY's drive setting is already at its best value. The display block clock (51.3 MHz, shared with the UARTs) also underruns above about 108 MHz; the stock software runs it at 102.6 MHz. The remaining suspect is a supply or reference the stock boot chain sets up and ours does not.
- The default is the sink's native mode, which is 1080p30 on a 4K TV, so `j33iap` overrides it: `apple,preferred-mode = "1280x720@60"` in the display node starts the board at 60 Hz. Write the same value to `/sys/module/s5l8947x_drm/parameters/preferred_mode` to change it at runtime (the kernel command line form `s5l8947x_drm.preferred_mode=` also works), and an empty value returns to the native-mode policy. When the sink's EDID does not list the requested resolution, the driver adds the standard 60 Hz modes the pipe can drive.
- The plane scans out XRGB8888 at 1:1 with no scaling, and the fbdev framebuffer is a single buffer: an application has to produce a full 32-bit frame per update, with no hardware upscale.
- There is no vertical-sync interrupt: the output stage's status register only carries error bits (the stock driver enables just those), and no frame/vblank source is wired to the display node's three lines. Measured on 2026-11-01 at 720p60: `.../irq_probe` reports all three lines silent with the output-stage enable at 1, its status at 0 and HPD at 1. The driver therefore synthesizes a vblank with an hrtimer at the mode refresh: page flips complete on the next tick, `DRM_IOCTL_WAIT_VBLANK` and `FBIO_WAITFORVSYNC` block, and commits are paced at the refresh rate (measured at 720p60: `fbtest -v` blocks and runs at 60.0 fps, 16.68 ms per frame). The timer runs free against the PHY, so it gives pacing but does not lock the plane update into blanking; tearing is reduced, not removed. `s5l8947x_drm.vblank_sim=0` returns to immediate flip completion. The probe takes a line number from the attribute's first line (73/74/75, the Linux view of hardware 44/46/47) and a second value sets the output-stage interrupt-enable register for the probe and restores it (`echo 73 1 > .../irq_probe`).
- The output gamma LUT, loaded with 256 entries per component, posterizes the picture and crushes the darks; it is bypassed at full brightness and used only when `gamma_brightness` is lowered. Its real entry format is unknown.
- The driver redoes the full mode set when it takes over the loader's 1080p30 scanout, so the sink blanks briefly.

### Central DMA known limits

- The device-address register holds only 24 bits; the upper address window comes from the channel's hardware wiring rather than a register. Two peripheral FIFO windows are measured and accepted by `s5l8947x-cdma`: `0x34000000` (audio, memory to device) and `0x31000000` (NAND FIFOs on channels 5–8, device to memory), while channels 1 and 2 are driven directly by `s5l8947x-aes`. Other peripheral clients (UART1/2, SHA, display) are still refused until their FIFO windows are verified.

### Audio known limits

- Optical output is not verified on a receiver; its DMA runs at real time. It plays 46 875 Hz only (one word per channel needs MCLK / 512).
- Optical still runs from the 24 MHz reference; exact rates there need the S/PDIF transmitter on PMGR oscillator 4 and a receiver to verify it.
- HDMI rates above 48 kHz (88.2 / 96 kHz) are not offered.
- The IOP core boots its own firmware but its scheduler panics before the message channel is up; the stock EmbeddedIOP control-message/endpoint protocol is not implemented.
- Channel order is reordered from the ALSA layout (FL, FR, RL, RR, FC, LFE, ...) to the CEA-861 order the sink expects; 8-channel uses side (SL/SR) for the fourth pair because CEA-861 has no distinct rear-side pair in the basic LPCM layout.

### SHA engine known limits

- The CPU feeds the engine one 32-bit write at a time, which caps it at about 15 MB/s; the engine alone hashes about 47 MB/s (SHA-256) and 76 MB/s (SHA-512).
- CDMA cannot feed it. The engine has a FIFO mode (mode bit 0: words written to `+0x20` fill the block and each full block is hashed), and the stock hardware description assigns it CDMA channel 4, request 1, but no setup moves data into it: programmed exactly as the stock CDMA driver would, the channel reports completion without reading the data or ends in an error, and a failed attempt leaves channel 4 busy in a way that stops other CDMA transfers (audio, NAND) until a reboot. The stock software never uses this path.
- Built-in ARMv7 and NEON crypto (`sha1-neon` 90.5 MB/s, `sha256-neon` 48.6 MB/s, `sha512-neon` 31.6 MB/s, `blake2b-512-neon` 58.3 MB/s, `chacha20-neon` 73.1 MB/s, `poly1305-neon` 221.4 MB/s, `cbc-aes-neonbs` 23.1 MB/s, `ctr-aes-neonbs` 33.9 MB/s) are also compiled into the kernel alongside `AF_ALG` hash and skcipher sockets.

### Scaler known limits

- The area-averaging footprint is clipped by the tap count beyond about 6x down horizontally (8 taps) and 2x vertically (4 taps), so thin horizontal lines can still alias when reducing more than 2x vertically. A two-pass scale (for example 2x then the rest) avoids it where it matters.
- Vertical reduction is limited to 7x in one pass; thumbnails from larger sources need two passes or a source crop.
- Crop and compose offsets are rounded down to whole chroma sites (even columns, and even rows for NV12).
- No rotation or mirroring ioctls yet, and only single contiguous buffers (no multi-planar API).
- The output alpha byte is `0xff` for a YCbCr source and carries the source alpha for an RGB source; there is no alpha control.

### JPEG known limits

- Baseline only: a progressive file fails with a stream error (status `0x10`).
- This block version has no decode-time downscaling (1/2, 1/4, 1/8); scale on the M2 scaler instead.
- No source-change events: the capture size is set by the application, and a larger image fails the buffer.
- Motion-JPEG frames without Huffman tables are untested.

### SGX known limits

- Presentation has three paths.  PRIME: `APPLE_SGX_BO_CONTIGUOUS` allocates one CMA block so its dma-buf has a one-entry scatter/gather table, and the `s5l8947x` display driver imports it (`sgxpresent`, verified on HDMI).  Screen blit: the display driver publishes its live scanout (`include/linux/s5l8947x-display.h`, generation-counted), the SGX driver maps it at `0x90000000` and reports it through `APPLE_SGX_PARAM_FB_*`, and `DRM_APPLE_SGX_BLIT` with `dst_handle` 0 copies onto it with no CPU copy and no modeset (`sgxpresent -s`).  EGL/GBM: Mesa's kmsro pairs the `apple_sgx` render node with the `s5l8947x` display, GBM gets contiguous scanout resources from the SGX driver, the display imports their dma-bufs, and page flips put them on HDMI (`gbmtest`, 300 frames on hardware).  The display's atomic commit waits on the render node's finished fence through the shared dma reservation (`drm_gem_plane_helper_prepare_fb`), verified by timing: 100 full-screen quads without `glFinish` delay the flip by the render's 390 ms.  Weston 14 (DRM backend, GL renderer, kiosk shell; `tools/weston/`) runs on the path with EGL and shm clients (`weston-run`), composited on the SGX and scanned out.  The render node still has no connector of its own (no KMS plane).  The 2D engine is usable from userspace through `DRM_APPLE_SGX_BLIT` (a scaled copy; the kernel builds the transfer), with `dst_handle` 0 copying onto the display's live scanout.  The TA/3D render queue runs on hardware: `sgxframe` clears 1280x720 and 640x360 through it, using the stock driver's event program carved from the device's own system image (SHA-256 `a1b855…`, the reference's template), and `stage2` tries every carved candidate and keeps the one that draws.  The screen mapping and `sgxpresent -s` are verified on hardware: the 2D engine's quadrants appear on the live scanout and `sgxframe -s` shows a GPU-rendered frame on HDMI.
- OpenGL ES 2.0 runs on the GPU. `tools/mesa-sgx/` carries the clean-room SGX Gallium driver (MIT, from the same work) with the port changes it needs (the event program's path, the frame directory default, the renderer string, and kmsro support), builds into Mesa 26.1.8 for Alpine armv7 (musl) in an armv7 container (`scripts/velliangiri.sh mesa`), and `tools/mesa-sgx/install.sh --system` makes it the system's GL. Verified on the device: `glclear` 0 pixels wrong (55-69 ms a clear with its read-back), `gltri` 11/11 checks, `glfs` 40/40 compiler cases, `glsize` 15/15 render-target sizes, `gltex` 14/14, `glblend` 14/14, `gldepth` 12/12, EGL on a GBM surface through kmsro (`gbmtest`, 300 frames flipped onto HDMI), and Weston with `weston-simple-egl` and `weston-simple-shm` on HDMI (scanout contents read back). The driver builds its frame with `sgx_template.c`/`sgx_rt.c` and takes only the stock driver's 0xa8-byte event PDS program from the kernel's firmware directory. The root is a ramfs, so `install.sh` leaves the install tarball on Data and `stage2` unpacks it at boot (verified after a DFU boot: "Mesa userspace unpacked from cache"). The desktop-GL half (GLX, x11/wayland) is an opt-in build (`MESA_BUILD=desktop`); the device has no X server, so it is checked through EGL's desktop OpenGL API (GL 2.1, `glclear-gl` 0 pixels wrong), while `libGL` and its X11/xcb dependencies load. See SGX.md and `tools/mesa-sgx/README.md`.
- The firmware is the device's own microkernel, carved by `sgxcarve`; the loader accepts only the module build whose UUID and region sizes it knows. A different stock image needs a new layout entry in `sgxcarve` and the driver.
- The SGX interrupt is not enabled by default (`apple_sgx.irq=1` turns it on at the next microkernel boot). Renders are polled by an hrtimer; the interrupt source has not been seen to fire.
- The GPU core clock reported to the microkernel is 256.5 MHz, the measured value for this GPU family. It only scales the microkernel's timers.
- Renders are serialised: one TA/3D job at a time, across all clients.

### NAND and FTL known limits

- The system keybag is unlocked with an empty passcode; on a device with a passcode set, classes 1–3 stay locked (`/sys/block/nand0/keybag` reports it). Keybags of a type with bit 30 set use another hardware key and are not supported.
- Seen once (2026-10-31, about 11 minutes after boot, first NAND read after roughly 10 minutes idle under the `ondemand` governor): every page read timed out waiting for the CDMA completion while the FMI transfer itself finished. Package resets did not clear it; switching the governor to `performance` did, and reads then worked at all three CPU speeds. A repeat of the same idle period on a fresh boot read cleanly, so the trigger is unknown.
- Wear levelling is by rotation only: free superblocks are taken in turn after the last one written, but no erase counts are kept. Garbage collection picks the superblock with the fewest live blocks.
- No discard (TRIM): Linux `hfsplus` never issues discards, so blocks of deleted files stay live in the FTL until overwritten. Garbage collection copies them like any other data.
- Superblocks that fail to erase are retired for the session (two did on 2026-10-31, status `0x45`, the status the package returns for its retired blocks); they are skipped again after the next map rebuild.
- Files created from Linux get no protection class: they are stored under the volume key only. `decmpfs`-compressed files are read-only (opening one for writing returns `EOPNOTSUPP`).
- `s5l8947x-fmi` spins for `spin_us` (default 5 µs) and then sleeps on the FMI interrupt (IRQ 33: sequencer status match, host transfer done). Measured at 850 MHz: 1024 single-page reads take 1.09 s at 30% CPU against 0.90 s at 98% when polling, and bulk reads run at about 47 MB/s at 48% CPU against 55 MB/s at 98%. The FTL map rebuild at boot takes about 6 s with either mode (measured 6.0 s polling, 6.1 s with the interrupt), so it is not bound by NAND waits. If an operation ever finishes without the interrupt, the driver logs it once and polls from then on. `FMI1` (`0x31300000`) is unpopulated on `j33iap`.

## Suggested order

1. SGX: OpenGL ES 2.0 runs on the GPU and reaches HDMI through EGL/GBM (kmsro), with implicit fences and a Weston compositor; next add input (USB host), then fill/rotation for the 2D engine.
2. NAND: reproduce the one-off CDMA completion timeout (stress reads across `ondemand` frequency changes) and make `s5l8947x-fmi` recover from it.
3. Add host mode to the OTG port.
4. Optical audio at exact rates: clock the S/PDIF transmitter from PMGR oscillator 4 and verify it on a receiver.
